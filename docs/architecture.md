- **Classification & Data Quality (Phase 5):** Deterministic, metadata-only classification proposals (versioned rules, confidence semantics, immutable history with input fingerprints); on-demand data-quality checks (missing metadata, invalid/unsupported extensions, conflicts, duplicate candidates, stale observations, source-mapping inconsistencies, unclassified) — never reads file contents, never mutates asset fields, never selects/executed a retention policy or lifecycle action. Classification writes require `classification:write` plus institution scope under the Phase 7 authorization boundary (ADR-0014); in production the auth layer fails closed rather than relying on the older blanket write guard (ADR-0010–0012). Frontend minimal view with loading/empty/error states and explainable evidence/warnings/conflicts.
- **Unified Review Workflow & Governance (Phase 6):** A single review queue (`GET /api/v1/retention/recommendations`) with server-side institution/review-status/recommendation/severity filters, permitted-metadata search, deterministic urgency/age sorting, and pagination; a read-only unified asset view (`GET /api/v1/governance/assets/{asset_id}`) aggregating inventory + source/scan, latest classification, quality findings, applicable policy and exact version, latest assessment and history, active holds, and append-only decisions with explicit provenance labels. Human decisions reuse the append-only `retention_decisions` table (`retain` / `request_more_information` / `approve_for_later_workflow` / `reject`), now race-safe via a unique `assessment_id` constraint (ADR-0013). Submissions carry optimistic-concurrency tokens and are rejected as stale (`409 stale_review_conflict`) or hold-blocked (`409 hold_conflict`); decisions are not execution commands and no archive/restore/move/delete is implemented.
- **Authorization on writes:** Every write route requires the appropriate permission plus institution scope (Phase 7, ADR-0014); out-of-scope writes receive the same 404 as missing resources and are audited. The older blanket production 503 guards (ADR-0010–0013) are historical and are not the current authorization boundary. Read-only operations remain available.
- **Identity, Authorization & Decision Supersession (Phase 7):** Server-verified identity via strict HS256 JWT bearer tokens (stdlib only) with issuer/audience/expiry/signature validation; production fails closed (503 `auth_not_configured:`) whenever the signing secret is missing or is the development placeholder, and the development sign-in provider is hard-disabled there (ADR-0014). Authorization is one `require_permission` dependency on every protected endpoint, backed by a local user directory that is authoritative over token claims; roles are viewer/reviewer/admin plus a platform administrator flag, out-of-scope resources answer 404 (no existence leak), and denied writes — permission failures and write scope failures — are audited (`authorization.denied`); scope-denial payloads deliberately omit the target institution id. Human decisions gain **supersession** (ADR-0015): a correction is a new decision linked by `supersedes_decision_id` (unique successor index, lineage/self-reference/cycle validated, effective decision derived server-side, full history preserved - no edit or delete path exists anywhere). The frontend adds sign-in/sign-out, permission-aware navigation and actions, institution scope selection, session-expired handling, and supersession/effective markers in the review history - all usability only; the backend re-authorizes every request. Migration `0011_platform_admin_default_false` corrects the unsafe `0008` platform-admin server default: it revokes ambiguous existing grants and sets future defaults to false (ADR-0017); a trusted operator must explicitly re-grant verified platform admins. Migration `0012_audit_platform_admin_reset` records the post-reset state in the append-only audit trail without changing access; it is forward-only evidence and cannot reconstruct revoked identities, so the pre-migration export remains mandatory. A read-only preflight (`scripts/migration_preflight.py`) reports the credential-free target and revision state before an operator applies migrations to an existing database, rejects non-MySQL dialects, and keeps backups and platform-admin re-grants as explicit human gates (ADR-0018). Migration `0010` repairs the `classification_results` downgrade inversion and sets the supported rollback boundary at `0005` with tested safe failure below it (ADR-0016). A real identity provider (RS256/JWKS) is **not** configured or claimed: production authentication stays fail-closed until an operator sets a real secret and IdP integration is implemented and tested.
- **Deployment Hardening (Phase 9):** A GitHub Actions workflow (`.github/workflows/ci.yml`, ADR-0019) is configured to run on pull requests and pushes to `main` on Linux (it has not yet executed on GitHub): backend and operator-script Ruff, backend tests, the 19-test live MySQL migration suite against an ephemeral `mysql:8.4` service, and the frontend typecheck/tests/production build, with no repository secret. The MySQL step fails when `MIGRATION_TEST_DB_URL` is absent and asserts that all 19 tests pass rather than skipped. GitHub Actions are pinned to full commit SHAs and the MySQL image to a verified digest. The local Windows PowerShell gate also lints the operator scripts and restores the caller's directory on failure. `docs/backup-restore.md` documents a verified restore drill on a disposable MySQL instance (21/21 table checksums, revision `0011` at drill time; current head `0012`, scratch database only), and `docs/production-readiness.md` records the unresolved production blockers (RS256/JWKS identity provider, secret management, TLS/reverse-proxy trust, database least privilege, audit/monitoring, backup automation, supply chain). No deployment, production connection, real identity provider, or durable-database migration was performed.
